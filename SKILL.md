# Godot Game Development

Turn the user's design into an editable Godot project, not a scripted imitation of one. Preserve the requested genre, dimension, style, controls, platform, scope, performance target, and existing project conventions.

## Non-negotiable outcomes

- Treat `.tscn` scenes and Godot resources as the authored game; use scripts for behavior, orchestration, procedural systems, and editor automation.
- Serialize persistent composition—actors, props, levels, cameras, lights, collisions, navigation, effects, and UI—so a human can edit it in Godot.
- Make reusable concepts reusable scenes and shared tunable definitions typed/external resources.
- Construct substantial runtime node trees only for genuinely procedural, data-driven, transient, streamed, or performance-driven content.
- Do not hide ordinary authored composition in `_ready()`, giant controllers, factory scripts, or long `Node.new()` chains.
- Never present raw primitives, default controls, mismatched assets, or unreviewed placeholders as finished design.
- For a new complete game or production slice, pass a builder-owned art-direction selection gate before bulk production. Preserve a user-fixed direction without forcing alternatives; otherwise compare materially viable directions against gameplay readability, identity, coherent asset/rights availability, content-scale consistency, animation/VFX workload, UI/localization/accessibility, target performance/size, maintenance, cost, and tool risk. Lock the selected layered contract plus a raw gameplay-size hero and representative composition; an easy pack, fashionable label, or generator default is not a decision.
- For a complete game or vertical slice, give the app/export icon and main menu identity a semantically legible relationship to the game and obtain an independent final-size review; palette consistency cannot turn arbitrary primitive geometry into a meaningful mark.
- For a complete game or vertical slice, pass a separate independent menu-craft review: use an authored wordmark or deliberate runtime typographic composition, keep only purposeful copy, and reject a generic badge/title/accent-line/tagline/identical-button-stack layout.
- For a complete game or production slice, pass one cross-surface independent craft review on the same exact candidate: main menu, pause/runtime modal, settings, ordinary play/HUD, result/failure, the text-heaviest secondary surface, critical icons, and integrated world/UI/telegraph/VFX frames. `authored`, `custom`, shared colors, equal node rectangles, and mathematical centering are implementation facts, not a quality verdict; blind first-read action/icon predictions and visible-pixel optical/family evidence are required.
- Standard consequential actions must be predictable in player language in every locale. Atmospheric synonyms may support tone but cannot hide whether an action resumes, restarts, creates a new save, advances, returns, purchases, or loses progress; copy and icon must predict the same outcome.
- Before calling production art complete, inspect raw target-build quiet, normal, dense interaction, peak VFX/contact, and result states. Scene serialization, materials, or shaders do not promote blockout primitives, debug-looking effects, broken contacts, sparse modules, or mismatched asset families to finished art; mathematically correct aim/trajectory/route telegraphs still need authored direction/contact/endpoint/validity semantics in the selected visual language.
- For a complete game or vertical slice, pass a separate gameplay-HUD glanceability gate: inventory every persistent/contextual text zone, remove or iconify redundant frequent telemetry, keep objectives action-oriented, prevent objective/prompt competition, use one accessible authored icon family with non-color cues, and obtain independent quiet/normal/dense/VFX review with representative localization.
- For a complete game or vertical slice, deliver coherent, licensed, integrated music/SFX and mixer controls unless the user explicitly requests a silent experience or non-production prototype. Code-synthesized beeps and generic tracks are placeholders, not finished audio.
- For every production character expected to move, autonomously pass a builder-owned motion gate before release: required idle/locomotion/context states run on the production visual, ordinary play never leaves it in bind/rest/T-pose, gameplay causes the state changes, animated attachments follow, and raw target-build motion is inspected. Do not make the user discover routine animation defects.
- For a complete game or vertical slice, prove from the clean shipping frame that an uncoached player notices the guidance, binds input to target, performs every required onboarding transition, reads feedback/consequence, and reaches the normal loop, then obtain independent UX/visual review across representative viewport extremes. Failure to discover the tutorial is a hard FAIL; static text, hidden state variables, one generic action, punitive pre-teaching pressure, seeded QA state, and the building agent's own screenshot approval are insufficient.
- Make complete-game duration/content claims auditable: map them to authored objectives, mechanic permutations/combinations, estimated solve time, and uncoached playtest evidence. A short slice must be labeled as a slice rather than scored as unbuilt hours.
- For every complete game where challenge, tension, risk, cognitive load, or competitive skill is material, declare a genre-aware difficulty envelope before bulk content. Track separate difficulty dimensions, learned-skill combinations, novelty, peaks/relief or player-selected risk, failure/recovery, and any adaptation boundaries; there is no universal curve, and a monotonic scalar ramp, HP inflation, grind, obscurity, or hidden ranked rubber-banding cannot self-certify good pacing.
- For material progression, upgrades, escalating challenge, rewards, resources, or meta-economy, declare project-specific balance budgets before bulk content; prove archetype/checkpoint coverage, viable choices, source/sink health, recovery, and model-to-build transaction parity. Separately prove visual comprehension of current state, next reachable goal, first reward/choice, cost/requirement, purchased/unlocked consequence, locked/late state, and the new decision an unlock creates. A deterministic model or localized text table cannot self-certify pacing, grind, fun, or player understanding.
- For persistent player or world state, use stable IDs and a versioned save envelope; prove clean creation, round trip, atomic/interrupted-write recovery, corruption fallback, every supported migration, idempotent load/settlement, and applicable device/cloud conflict in the target build. Current-version happy-path serialization is not a save contract.
- For procedural content, separate and version random streams, retain reproducible seeds, prove solvability and bounded fallback across a declared cohort, test distributions and save/resume parity, and review variety in actual play. Attractive hand-picked seeds cannot certify a generator.
- For gameplay AI, declare perception, information, navigation, recovery, telegraph, update cadence, and capacity contracts; prove occlusion, replan, unreachable targets, crowds, off-screen behavior, pause/save lifecycle, and readable fair motion. A behavior tree or one successful path is not acceptance evidence.
- For every promised input device and accessibility feature, prove critical-action reachability, remap/conflict/reset/persistence, hot-plug/focus recovery, truthful glyph/focus state, local-player ownership when applicable, and the actual behavioral effect of each setting. Labels and InputMap entries alone do not pass.
- Apply the relevant strategy/simulation, vehicle/racing, shooter/action, narrative/cinematic, or local-multiplayer contract when that system shapes the experience; builder-owned deterministic evidence establishes correctness, while required human or independent review establishes feel, pacing, comprehension, or simultaneous play.
- For online multiplayer, record topology, transport/platform support, authority, RPC validation/rate limits, replication identities, impairment budgets, reconnect policy, capacity, and persistence boundaries before dependent gameplay. Treat clients as hostile; one localhost process never certifies networking.
- For extraction games, make the raid/durable-state ledger explicit and prove successful extraction, death/loss, retry-safe settlement, stash reload, risk-route viability, and bankruptcy recovery in the target build; combat plus an exit marker is not a complete extraction loop.
- For MMO or persistent-online work, label scope honestly. A production slice requires real authoritative server and identity/persistence paths plus load, failure, observability, restore, and rollback evidence; local mocks and replicated demos cannot substantiate a complete or launch-ready MMO.
- For platform/store release, verify each exact candidate through clean install, update over an old save, missing/offline SDK, lifecycle/display/input recovery, configured services, signing/package identity, upload scope, and rollback; export exit code alone is not a release verdict.
- For mods or UGC, declare the trust tier and override/executable-code policy, validate hostile malformed/oversized/path-collision cases, prove dependency/removal/safe-mode recovery, and never claim sandboxing Godot does not provide or auto-execute unknown downloaded payloads.
- For localization, replay/ghost/spectator, large streamed worlds, native mobile, LiveOps, XR/console, runtime creator tools, or reproducible releases, apply the matching conditional contract and real target/runtime evidence. A translation table, editor preview, simulator, mocked hardware/backend, warm local build, or happy-path trace does not certify the feature.
- For promised crash recovery, commerce, accounts/cloud, online safety, engine/project upgrades, fault tolerance, desktop hardware coverage, or assistive access, compose the matching modifier case and pass its target-build contract plus required independent/human gate. SDK presence, a mock provider, structural accessibility metadata, one development PC, a clean editor import, or one happy path cannot certify these release claims.
- Compose evaluation cases from the smallest truthful base game case plus every material modifier. Applicable gates are the fail-closed union and score floors are the per-dimension maximum; never choose one convenient case to omit a promised system.
- Keep completion responsibility-scoped. Continue autonomously while any builder-owned gate, routine defect, or failed external review still requires a builder fix. Once the exact candidate and all available builder-owned QA pass, report `BUILDER_COMPLETE / READY_FOR_HUMAN_TEST` even when a genuinely human, independent, provider, hardware, or publication check remains unavailable; reserve `PUBLICATION_CERTIFIED` for a candidate that passed those external gates too. Do not replace either status with a user to-do checklist.
- For an open-ended new complete game, stop after a representative playable slice and obtain explicit product-owner approval or waiver of the core loop/concept and visual direction before multiplying levels, chapters, progression content, or expensive asset families. Independent clarity/craft review cannot certify that the owner likes the product idea.
- If the user/product owner explicitly closes or cancels a project, preserve the failure packet and stop with the non-success terminal `PROJECT_CLOSED / USER_REJECTED`; never claim READY/PUBLICATION, continue repairs, or turn closure into a checklist unless the user later reopens the work.
- For fixed-camera isometric/orthographic complete work, block bulk level authoring until a rendered gameplay-size slice—hero, mechanism states, objective, decor, lighting, and UI—passes independent review; later prove character/background separation, route readability, and density/composition in the target camera.
- For fixed/high-angle 3D districts, arenas, settlements, or extraction routes, pass builder-owned district-composition, local environment-integrity, whole-map coverage, whole-perimeter visible-first boundary, and road/streetscape-semantics contracts. Bind all reports to one deterministic resolved dependency-closure digest covering the root scene, recursive/runtime resources, evidence exporters, project settings and selected export preset; a root `.tscn` hash is not a candidate revision. Resolve final transforms; prove full-footprint occupancy, strict visual plausibility for intentional contacts, and topmost surface/object relationships; partition the playable footprint into single-family zones with fallback/adjacency budgets; tile-survey every cell through the shipping camera; compare every enabled static collider and hero-radius blocked sample to visible render mass; prove every declared perimeter ray/capsule contacts mapped visible geometry before any safety-only wall with clearance; independently flood-fill an exporter-owned grid using the actual production hero capsule against a nonempty unsafe fringe; retain each visible limiter or prove mapped replacement continuity; and prove resolved production occluder aliases fade/restore. Where streets exist, also prove lane/junction/approach/sidewalk/crosswalk topology; exporter-owned marking mesh chains and endpoint distances; typed road-end policy with topmost before/at/between/beyond samples—road continues through vehicle cordons but road and markings stop before facade/terrain ends—with no surrogate closure plane or marking beneath a cap; center-and-edge sidewalk/curb-return continuity on every approach and T-side; crosswalk priority over drains/repairs; class-specific building/vehicle/vegetation/hydrant/lamp/signal/detail forbidden-surface footprints; exporter-owned complete visible-mesh classification; exporter-owned scene metadata for facade/roof/openings/trim source roles bound to actual mesh surfaces or source texture/UV masks; target-build pixel value/chroma/variation/dominant-color/separation; every visible furniture subclass; resolved support-vertex to ground/mount-mesh contact; street-furniture setback/orientation; authored incident closures; and zero reachable pockets against safety-only walls. Legal origins, adapter-authored boundary cells, deleted visible limiters, adapter-invented source roles/slots/percentages/distances, a common road mesh or dark plane named as a cap, sidewalk slabs across lanes, facade/roof normal masks that omit windows/trim, flat facade flood fills, scalar zero-gap mounts, resource-only color checks, omitted lamps/poles/supports, bare road cuts, floating supports, a prose-only overlap exemption, one permissive ground region, curated captures, complete collision/navmesh coverage, 100% node-level material assignment, synthetic camera fixtures, zero flood-fill pockets, cars merely named as a boundary, attractive stills, exporter error followed by output/PASS, or root-only provenance cannot certify the map.
- Keep QA/evidence adapters, report generators, fixtures and local mocks out of production scene/runtime dependency closures. Inject them transiently from the QA process and hash them as toolchain inputs. After every exact shipping export, scan PCK/embedded executable/archive entry names and bytes for declared QA/report/mock namespaces and project-specific forbidden markers; export filters and exit code cannot prove absence of referenced dependencies.
- Do not claim polish, performance, memory, or size improvements without testing the relevant built/rendered result.
- Keep the result maintainable and editable after the agent finishes.

## Inspect before changing

Locate `project.godot`; inspect its Godot features/version, renderer, language, main scene, input map, autoloads, plugins, display/export settings, nearby scenes/resources/imports, conventions, and version-control state. Start with a bounded snapshot instead of dumping the repository:

```bash
python <skill-dir>/scripts/project_snapshot.py --project <project-dir> --summary --json-output <report.json>
```

Then read only the task-relevant scene/resource dependency chain. Determine the available editor/CLI version. Do not silently migrate the engine, renderer, language, addons, or project-wide settings.

Extract the actionable brief from the user's words and references. Infer reversible details when safe; ask only when a missing decision materially changes the result. For a new project, use the installed Godot 4 editor and GDScript unless the user specifies otherwise.

## Keep context efficient

- Map the project with scoped file/path searches before opening large scenes or scripts; ignore caches, imports, generated builds, and binaries unless the task targets them.
- Prefer Godot/CLI/project-owned input and capture evidence. Use desktop Computer Use only with explicit user opt-in or for otherwise unreachable native OS behavior, never merely to click the game or take routine screenshots.
- Read the relevant scene/resource dependency chain and changed regions instead of repeatedly dumping the repository or whole large files.
- Prefer compact console summaries with full diagnostics written to report files. Use `--summary`/`--json-output` where bundled auditors support them.
- Preserve durable decisions in scenes, resources, manifests, budgets, or short project notes rather than restating them every turn. Never trade away verification or maintainability merely to save tokens.
- For a long run, keep one compact `project-run-state` record with the current playable truth, exact commands, build/evidence IDs, asset/cost state, next bounded actions, and blockers. Update it only at meaningful checkpoints so it replaces repeated rediscovery rather than becoming another log.

## Execute in authored slices

Build the smallest complete slice that demonstrates the requested experience: establish scale/camera/input plus visual and sonic language, create reusable scenes/resources, compose the playable scene, add focused behavior, integrate representative production assets including audio, run it, inspect representative states, and iterate. For a new complete game/slice, do not multiply assets or levels until `assets/art-direction-selection.template.md` records the selected direction and its gameplay-size anchor; a user-fixed direction uses the same production translation without artificial alternatives. For an open-ended complete game, also do not multiply content until the exact playable slice receives the explicit product-owner decision recorded in `assets/product-owner-slice-decision.template.md`; an owner may approve, request revision, explicitly waive the checkpoint, or close the project. For fixed-camera isometric/orthographic work, also pass the stronger representative art/readability gate. For fixed/high-angle 3D district work, prove one representative route with visible boundary causes, massing/landmark hierarchy, functional story zones, modular variation, clean local contacts plus whole-map surface/collider/camera coverage, whole-perimeter visible-first contact order, and camera-motion restoration before multiplying districts or dressing. For every production slice, inspect dense interaction and peak effects before multiplying the art direction; a quiet frame is not an art gate. Do not postpone all sound until after the gameplay and presentation are otherwise declared complete.

Use direct `.tscn`/`.tres` edits for small understood structures; use the Godot editor for visual placement and fragile serialization; use `EditorScript`/`@tool` for repeatable bulk authoring; use appropriate content tools for source assets. Generated output must remain normal Godot scenes/resources. Never edit `.godot/` cache contents as source or invent UIDs when safer editor/path workflows exist.

## Handoff truthfully

Report the scenes/resources/assets changed and how they compose; commands/tests/builds run; rendered or profiled states inspected; intentional runtime-generated content; performance/size baselines and deltas when relevant; and remaining placeholders, license obligations, dependencies, or unverified states. If the user has not watched or played the current target build, include a short deterministic proof recording that progresses through representative gameplay and that the builder watched back in full; it supplements rather than replaces the raw state matrix, playtest, or independent/human gates. For a complete game/slice, run the rubric scorecard against evidence with real reviewer provenance and structured artifact paths.

End a successful handoff with exactly one responsibility status:

- `BUILDER_COMPLETE / READY_FOR_HUMAN_TEST`: all builder-owned work that is available and authorized is finished, the exact candidate and review packet are ready, no known external-review failure remains unfixed, and only genuinely external evidence is pending.
- `PUBLICATION_CERTIFIED`: the same candidate also passed every applicable independent, human, provider, hardware, and publication gate.

If neither is true, keep working; do not hand off a candidate with builder-owned work remaining. A pending external gate remains `NOT TESTED` in evidence and prevents publication certification, but it does not turn a builder-complete candidate into a vague `NOT READY`. State the evidence boundary in one concise sentence. Do not finish with obvious instructions such as opening a dashboard, uploading the ZIP, or conducting a human test unless the user explicitly asks for that publishing/testing workflow.

An explicit user/product-owner decision to end the project is the sole additional terminal: emit `PROJECT_CLOSED / USER_REJECTED`, record `project_disposition.status=user_closed` plus the decision context, preserve unresolved gates and postmortem artifacts, and stop. This is not successful completion and must not be used as a substitute for finishing difficult builder-owned work.
